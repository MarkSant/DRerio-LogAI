# A8 — one end-to-end test per user flow (TASK-087)

The four flows run OPPOSITE contracts over the same code: a pre-recorded
PROJECT, a SINGLE VIDEO without project, a LIVE PROJECT and an AD-HOC LIVE
session without project. A change that is right for one is a regression in
another. This front gives each flow one test that drives the production entry
points as far as a headless run allows and asserts that flow's OUTPUT CONTRACT,
derived from the input, so a regression in any flow fails CI.

Fakes are allowed only at the hardware/process boundary: camera frames, the
model (a deterministic plugin), the worker process, the Arduino.

## Flow 1 — pre-recorded project

**Added:** `tests/integration/test_flow_e2e_prerecorded_project.py` (default CI
job, ~4 s for the module; the processing runs once, in a module fixture).

**Drives:** `VideoProcessingCoordinator.process_pending_project_videos` on a real
`ProjectManager` project in `tmp_path`, with the real selection / validation /
classification services, the real `ProcessingWorker` monitor thread, the real
`_WorkerProcess.run()` loop, the real `VideoCompletionMixin` and the real
`ReportGenerationCoordinator` + `AnalysisService`.

**Faked** (shared harness `tests/helpers/flow_e2e.py`): `_WorkerProcess.start`
runs `run()` in-process (`is_alive`/`join` follow); the YOLO plugin class the
worker imports (`zebtrack.plugins.ultralytics_detector.UltralyticsDetectorPlugin`)
becomes `GoldenDeterministicPlugin` — the rest of `_initialize_detector`
(zone scaler, single-subject mode, restoring the context's zones) stays real;
the worker's `configure_logging` is a no-op.

**Configuration:** zones are saved exactly as the Zones tab saves them (raw video
pixels, no source size) and `camera.desired_width/height` equals the video size
(640x480). That is the configuration under which the flow is correct today; the
shipped 1280x720 reference exposes A8-001/A8-002.

**Input:** two BYTE-IDENTICAL videos `videos/Dia_1/CECT_4/CECT_4.mp4` and
`videos/Dia_2/CECT_4/CECT_4.mp4` (same stem, same sha256), metadata group `CEC`,
subject 4, days 1 and 2; day 1 gets the whole tank as arena, day 2 only the right
half.

**Asserts:**

- each day's `1_ProcessingArea_`, `3_CoordMovimento_`, `4_Relatorio_*.docx` and
  `.xlsx` land in `project/Grupo_CEC/Dia_0N/Sujeito_04/`;
- nothing is written next to the source videos;
- the trajectory has the immutable column order and rows;
- day 2's detections all lie inside ITS arena while day 1 keeps the left half,
  and the two `1_ProcessingArea_` files differ (arena of A not used for B);
- the trajectories and `.xlsx` of the two days differ (day 2 did not overwrite
  day 1);
- each project entry is `processed` and registers its own trajectory, `.docx`,
  `.xlsx` and `results_dir`;
- the two entries share sha256 and stem: only the path tells them apart.

**Negative control (run by hand, not committed):** giving day 2 the arena of
day 1 turns `test_each_video_was_processed_with_its_own_arena` and
`test_day_two_did_not_overwrite_day_one` red.

**Seams missing:** none needed beyond monkeypatching the process boundary.
`ProcessingWorker` has no injectable worker factory and `_initialize_detector`
imports its plugin class inside the method; the harness patches
`_WorkerProcess.start/is_alive/join` and the plugin class at their import site
instead (reported, not added). A `worker_factory`/`plugin_factory` parameter would
let these tests stop monkeypatching.

**Defect test:** `test_project_worker_receives_the_zone_source_size`
(`xfail(strict=True)`, A8-002).

**Observation (not a defect claim):** after the run, the entry's
`parquet_files.arena`/`rois` are `None` although `has_arena`/`has_rois` are
`True` and the `1_`/`2_` files exist in the subject folder. Readers that trust
`parquet_files` over the flags would not find the zones of a processed video.
Not asserted; worth a look by whoever owns `OutputRegistrationManager`.

## Flow 2 — single video (no project)

**Added:** `tests/integration/test_flow_e2e_single_video.py` (default CI job,
~3 s for the module).

**Drives:** `VideoProcessingCoordinator.start_single_video_processing` — what
`VIDEO_START_SINGLE_PROCESSING` and `AnalysisControlViewModel` call — on a
`ProjectManager` with NO project, then the same real worker / completion / report
chain as flow 1. Same fakes, same harness.

**Asserts:**

- `1_ProcessingArea_`, `2_AreasOfInterest_`, `3_CoordMovimento_` and
  `4_Relatorio_<stem>.{docx,xlsx}` land in `<video_dir>/<stem>_results/`, and the
  input folder holds only the video and that folder;
- no `project_config.json`, no `config_snapshot.yaml`, no `Grupo_*` anywhere, and
  the manager still has no `project_path`;
- the trajectory has the immutable column order and covers the whole arena
  (x from < 200 to > 400 px);
- the `.xlsx` carries the ROI drawn for this video;
- the video is registered in memory only (group `single_video`), with its report.

**Report names — documentation drift:** CLAUDE.md says the single-video pipeline
writes `<video>_report.docx` and `<video>_summary.xlsx`. The production entry
point writes `4_Relatorio_<stem>.{docx,xlsx}`, like the project: it ends in
`ReportGenerationCoordinator._export_individual_outputs`. The `_report`/`_summary`
names come from `AnalysisPipelineRunnerMixin._generate_reports_for_video`,
reachable only from `VideoProcessingService.process_single_video`, whose callers
are `AnalysisControlViewModel._process_single_video` and, through it,
`AnalysisService.process_videos_batch` — and nothing in `src/` calls
`process_videos_batch` (only `tests/analysis/`). The test pins what the
flow produces; CLAUDE.md's "Output Structure" note should be corrected by whoever
owns it.

**Defect test:** `test_arena_is_honoured_when_the_video_is_not_the_camera_size`
(`xfail(strict=True)`, A8-001).

## Defects

### A8-001 — single-aquarium zones are scaled from the camera reference, not from the video

**Status:** open, red test committed as `xfail(strict=True)`
(`test_flow_e2e_single_video.py::test_arena_is_honoured_when_the_video_is_not_the_camera_size`).

The Zones tab stores arena/ROI points in the video frame's own pixels
(`VideoDisplay.canvas_to_video`), the report reads them as raw pixels
(`_generate_standard_report`), and `COORDINATE_SYSTEMS.md` says "User-drawn Arena
and ROI polygons: Original Video Space". Nothing writes
`source_video_width/height` into a single-aquarium `ZoneData` (only the
multi-aquarium paths do). The worker's `_initialize_detector` builds the
`ZoneScaler` with `camera.desired_width/height` (1280x720 shipped) and, without a
source size, `_process_single_video` keeps that base: the arena is scaled by
`video_size / camera_size`. A 640x480 video gets an arena half its drawn size;
the subject's walk to x = 500 px is dropped as "outside the arena"
(`x_center_px.max() == 299.5`, the scaled edge) while the run reports success.
Both pre-recorded flows are affected whenever the video's resolution differs
from the machine's camera reference. `_repair_source_dimensions_if_needed` only
runs when a source size exists, so it never helps here.

### A8-002 — the project batch drops the zone metadata on the way to the worker

**Status:** open, red test committed as `xfail(strict=True)`
(`test_flow_e2e_prerecorded_project.py::test_project_worker_receives_the_zone_source_size`).

`VideoSelectionMixin._load_zones_for_eligible_videos` rebuilds
`video_info["zone_data"]` with `polygon`, `roi_polygons`, `roi_names` and
`roi_colors` only. Even a zone that DOES carry `source_video_width/height` loses
it, so the worker falls back to the camera reference (A8-001's mis-scaling) in the
project flow; the single-video path keeps the metadata (it serialises the whole
`ZoneData` in `ProcessingWorker.start_in_thread`). Causality checked out of tree:
restoring the metadata in that dict makes the red test pass. Fixing A8-001 by
recording the source size at save time would still be defeated by A8-002, so the
two go together.
