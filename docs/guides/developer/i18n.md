# Internationalization (i18n)

English is the source language of DRerio LogAI. Every user-visible string is
written in English in the code, and Portuguese lives in a translation catalogue.
A missing translation therefore falls back to the English text rather than to a
placeholder — which is why "English is the default" costs nothing to maintain
and there is no `en` catalogue.

## Adding or changing a string

```python
from zebtrack.i18n import _

ttk.Button(parent, text=_("Save project"))
```

Then regenerate the catalogues:

```bash
poetry run python scripts/update_translations.py
```

Fill any remaining `msgstr ""` in
`src/zebtrack/locales/pt_BR/LC_MESSAGES/zebtrack.po`, run the script again to
recompile the `.mo`, and commit the `.po`, the `.mo` and the `.pot`.

CI fails on an empty `msgstr`, on a fuzzy entry, and on a `.mo` that does not
match its `.po`.

## Interpolation

Use `.format()`, never an f-string. An f-string is evaluated before `_()` sees
it, so the msgid would contain the interpolated value and never match the
catalogue:

```python
_("Removed {count} videos").format(count=n)   # correct
_(f"Removed {n} videos")                      # never matches; do not do this
```

## The two domains

| Domain | Covers | Reached through |
| --- | --- | --- |
| `zebtrack` | Everything the GUI says | `from zebtrack.i18n import _` |
| `reporter` | Headings and labels inside generated `.docx`/`.html` reports | `from zebtrack.analysis.reporters.reporter_context import _` |

Both follow the same `ui.language` setting. They are separate files so that the
stable scientific vocabulary of the reports does not churn with every UI change.

## When the language is decided

`ui.language` in `config.local.yaml` is the only authority. The operating system
locale is deliberately **not** consulted — before v5.0.0 a Brazilian Windows
install silently produced Portuguese reports nobody had asked for.

The order in `core/app_runner.run_app()` is:

```text
logging → Tk root → first-run language prompt → load_settings()
        → i18n.install(settings.ui.language) → splash → build the UI tree
```

`i18n.install()` must run before the UI tree is built. The prompt runs before
`load_settings()` because answering it writes the file that `load_settings()`
then reads.

For tests and CI, `ZEBTRACK_LANGUAGE` overrides the setting and
`ZEBTRACK_SKIP_LANGUAGE_PROMPT=1` suppresses the first-run dialog. Both are set
in `tests/conftest.py`.

## Never call `_()` at import time

`_()` resolves the catalogue when it is *called*. A call in a module or class
body runs at import — possibly before a language has been installed — and
freezes that result into a constant. The symptom is one label stuck in the wrong
language, with nothing in the logs, reproducing only when import order shifts.

```python
# Wrong: evaluated at import.
PROJECT_STATUS_META = {"ok": (_("Ready"), "green")}

# Right: evaluated per call.
def project_status_meta():
    return {"ok": (_("Ready"), "green")}
```

`tests/i18n/test_no_import_time_translation.py` fails the build on this. When
turning the constant into a function would ripple through many call sites,
`zebtrack.i18n.lazy()` returns a proxy that resolves on each read — but it is
not a real `str`, so never use it as a dict key, in a `set`, in a `match`, or
anywhere it can reach pandas, Pydantic or `json`.

## What must never be translated

Some Portuguese strings are data, not copy. Translating them does not produce an
English application — it produces one that cannot read the projects it wrote
yesterday. They are listed in `scripts/i18n_allowlist.txt`:

- **Output directory names** — `Grupo_*`, `Dia_*`, `Sujeito_*`, `Sem_Grupo`,
  `Dia_Indefinido`, `Sujeito_Indefinido`, and the rescan regexes in
  `core/project/metadata_manager.py` that must keep matching existing folders.
- **`session_duration_overrides` keys** built by
  `core/services/session_duration_resolver.duration_override_key()`. Renaming
  the prefix orphans every stored override **silently**: no exception, the
  duration just falls back to the project default mid-recording.
- **The `por_animal` sheet name** and its `PER_ANIMAL_COLUMNS`, which
  third-party scripts read by name.
- **Report dict keys** — `comportamento_geral`, `analise_roi`, `validacao`,
  `avisos`, `log_eventos`.
- **Cross-module sentinels** compared with `==` far from where they are
  produced: `"Todos"`, `"Sem Dia"`, `"Não informado"`, `"Arena Principal"`.
  These should become real constants; until then, translate only where they are
  rendered.

Where such a token is *displayed*, translate at the display boundary — render
`_("Unassigned")` for a stored `Sem_Grupo` — and never change what is stored.

## Exception messages

Exception text that only reaches logs and tracebacks stays in plain English and
is **not** wrapped in `_()`; translated log text is harder to search and to
share in a bug report. Validation errors that the UI renders verbatim to the
user (`show_error(..., str(exc))`) *are* wrapped.

Never branch on the words inside an exception message. `except SomeError:`
survives translation; `if "caminho não definido" in str(e)` does not, and it
fails by silently taking the wrong branch.

## Adding a language

1. Add it to `SUPPORTED_LANGUAGES` in `src/zebtrack/i18n.py` and to the
   `Literal` on `UISettings.language` in `settings.py` — a test asserts these
   two stay in step.
2. Add it to `LANGUAGE_CHOICES` in `src/zebtrack/ui/language_dialog.py`.
3. Run `pybabel init -i src/zebtrack/locales/zebtrack.pot -d src/zebtrack/locales -l <code> -D zebtrack`
   (and the same for the `reporter` domain), then translate and run
   `scripts/update_translations.py`.

## The migration

The UI is being converted from hardcoded Portuguese in stages. Two tools support
it:

- `scripts/i18n_scan.py` lists Portuguese literals that still need extracting
  (`--format=count` for a per-file tally).
- `src/zebtrack/locales/_pairs/*.json` record `{english_msgid: original
  Portuguese}` as each batch is rewritten, and `scripts/i18n_pairs.py` merges
  them into the catalogue. The Portuguese literal *is* the translation, so the
  migration is a move, not a translation job — and a reviewer can check that the
  `.po` diff is the exact inverse of the source diff.

`tests/i18n/test_no_untranslated_literals.py` holds the list of packages already
migrated and fails if one of them gains a new Portuguese literal. Extend that
list in the same PR that migrates a package.
