# Barnes maze — validating and calibrating against the lab's manual scoring

**Tool:** [`scripts/barnes_validation.py`](../../../../scripts/barnes_validation.py) ·
**Tests:** `tests/scripts/test_barnes_validation.py` · **Plan:** [PLAN.md](PLAN.md) §5 ·
**Contracts:** [CONTRACTS.md](CONTRACTS.md) §3.2 (`BarnesParams`), §6–§7 (metric semantics).

The Barnes metrics of the app (`report["protocol_metrics"]`) depend on thresholds that are
provisional: `visit_min_cover`, `visit_enter_frames` / `visit_exit_frames`, `center_radius_ratio`,
`entry_min_cover`, `entry_max_visible_fraction`, `entry_hold_s`, `entry_absent_s` and the strategy
thresholds. They were chosen from the protocol and from reading the code, **not** from data. This
tool compares the app's numbers with the lab's own manual scoring and tells you how well they
agree; with the `calibrate` mode it also searches for better values and checks them on videos it
did not use to choose them.

Nothing here changes a project: the tool only reads. A calibration ends in a *suggested*
`protocol_params.barnes` block that you paste (or not) yourself.

## 1. What you have to export

Three spreadsheets (`.xlsx` or `.csv`) with the lab's manual scoring, **plus the videos (or the
app's results for them)** the scoring refers to. Aim for at least **30 trials**, spread over the
groups and days, and **keep the awkward ones**: rats that never entered (240 s), trials placed by
hand, probe trials. A calibration cannot learn what the sample never shows.

The column titles and the order are up to the lab — the mapping file (§2) says which column is
which. What matters is that each sheet has **one row per trial**, that every trial can be
identified (group + day + subject, or the video file), and these values:

### 1.1 Latencies (training trials)

One row per trial. Times in seconds (`83.5`, `83,5`) or as `m:ss` (`1:23.5`); an Excel time cell
also works.

| Grupo | Dia | Animal | Tentativa | Início (s) | Latência encontro (s) | Latência entrada (s) | Erros primários | Erros totais |
|---|---|---|---|---|---|---|---|---|
| CBD | 1 | 7 | 1 | 5 | 38,1 | 41,7 | 2 | 3 |
| CBD | 1 | 8 | 1 | 7 | 240 | 240 | 9 | 14 |

* **Início** is the *manual START* — the instant the rat was released and the experimenter was
  gone, read from the video. It is what the app's own START (the analysis window) is compared
  with. If the lab does not record it, leave the column out: the START comparison is then simply
  not made.
* **Encounter** = nose poke into the escape hole; **entry** = four paws in. A rat that does not
  enter, or is placed in the hole by hand, is scored **240 s** (the lab's rule). The tool treats a
  value ≥ the ceiling as **censored — "did not happen"** — never as a measurement (§4.2). If the
  lab marks it in a yes/no column instead of (or besides) the 240, map that column too.
* The error columns are optional; they are what calibrates `visit_*` best, so include them if the
  lab has them.
* **Tentativa (trial)** is needed whenever an animal has more than one trial per day (the lab's
  working-memory protocol runs 3 per day, reference memory 2): group + day + subject then no longer
  identify a row. Put it in every sheet, add `trial` to `match.keys` and see "Matching" below for how
  the app side gets its trial number. With one trial per animal per day, leave it out.

### 1.2 Search strategy

| Grupo | Dia | Animal | Estratégia |
|---|---|---|---|
| CBD | 1 | 7 | Seriada |

The labels may be in any spelling of direct / serial / random; `direta`, `seriada`, `aleatória`
and the English words are built in, and anything else goes in the mapping's `label_map`. A label
the tool does not know is **reported**, never guessed.

### 1.3 Probe

| Grupo | Dia | Animal | Score 1º buraco | Latência 1º erro (s) | Tentativas |
|---|---|---|---|---|---|
| CBD | 4 | 7 | 4 | 12,3 | 3 |

* *Score of the first hole*: the lab's number for the hole the rat visited first.
  **Confirm with the lab** that it is `min(distance + 1, 10)` (target = 1, +1 per hole away, the
  opposite hole = 10): that is what the app computes (`probe_score`, CONTRACTS §3), and this
  comparison is how that assumption gets checked.
* *First-error latency* is blank when the first hole was the target (the app also leaves it
  blank); a blank on both sides counts as agreement.
* *Attempts*: visits up to and including the first visit to the target.

### 1.4 The app's side

Either of these (§3 explains when to use which):

* the **unified report** of the project (`unified_reports/total/unified_summary_*.parquet`) — it
  must be generated by a version of the app that writes the `barnes_*` columns (the
  `barnes-reports` stage of v8.1); or
* the project's **results folder** (the `3_CoordMovimento_*`, `1_ProcessingArea_*`,
  `2_AreasOfInterest_*` and `3c_Objetos_*` files, in the app's own
  `Grupo_*/Dia_*/Sujeito_*` layout) and, ideally, `project_config.json`.

The videos themselves are **not** read by this tool; keep them so a disagreement can be looked at.

## 2. The mapping file

```powershell
python scripts/barnes_validation.py init-mapping --out C:\lab\barnes_mapping.yaml
```

writes a commented example. Edit it so each `columns:` entry holds the **header text** of the lab's
sheet (case, accents and stray spaces are tolerated). A field the lab does not record is simply
left out. Paths are relative to the mapping file.

```yaml
match:
  keys: [group, day, subject]      # how rows are matched (see below); add `trial` for 2-3 trials/day
  use_video_path: true
  allow_unique_basename: false
  aliases:
    group: {controle: ctrl}        # lab spelling -> app spelling, per field

sheets:
  latencies:
    file: latencias.xlsx
    sheet: Plan1                   # xlsx only; default: first sheet
    header_row: 1                  # 1-based row of the titles
    censor_at_s: 240               # lab value >= this means "did not happen"
    columns:
      group: Grupo
      day: Dia
      subject: Animal
      video: Video                 # optional, see "Matching"
      start_time_s: "Início (s)"
      encounter_latency_s: "Latência encontro (s)"
      entry_latency_s: "Latência entrada (s)"
      encounter_censored: "Não encontrou"   # optional yes/no column
      entry_censored: "Não entrou"          # optional yes/no column
      primary_errors: "Erros primários"
      total_errors: "Erros totais"
  strategy:
    file: estrategia.xlsx
    columns: {group: Grupo, day: Dia, subject: Animal, strategy: Estratégia}
    label_map: {direta: direct, seriada: serial, aleatoria: random}
  probe:
    file: probe.xlsx
    columns:
      group: Grupo
      day: Dia
      subject: Animal
      probe_score: "Score 1º buraco"
      first_error_latency_s: "Latência 1º erro (s)"
      attempts: "Tentativas"

app:
  columns: {}                      # only if the unified file's headers differ (see §3.1)
```

| Field (per sheet) | Meaning |
|---|---|
| `group`, `day`, `subject`, `trial`, `video` | Identify the row (at least one required). |
| `start_time_s` | Manual START, any sheet. |
| `encounter_latency_s`, `entry_latency_s` | Latencies (latencies sheet). |
| `encounter_censored`, `entry_censored` | Optional yes/no columns; ORed with "value ≥ `censor_at_s`". |
| `primary_errors`, `total_errors` | Error counts (latencies sheet). |
| `strategy` | Strategy label (strategy sheet). |
| `probe_score`, `first_error_latency_s`, `attempts` | Probe sheet. |

Optional per sheet: `encoding`, `delimiter` (csv), `header_row`, `censor_at_s`. A mistake in the file
(unknown sheet or field, a column the sheet does not have, a label the map cannot place) stops the
run with a message listing what *is* there — exit code 2.

### Matching lab rows with the app's rows

The same file name repeats across days (`Dia_1/CECT_4/CECT_4.mp4` and `Dia_2/CECT_4/CECT_4.mp4`
are different trials), so a bare name is **never** used on its own. In this order, the first rule
that finds a candidate decides:

1. **Video path** — the lab row has a `video` with two or more path components: the app row
   sharing the **longest** trailing run of components (at least two) wins; a tie is *ambiguous*. A
   lab row that has such a path and finds **no** app video is reported as **unmatched** — it never
   falls through to the key, because the key could pair it with another trial of the same animal.
   (If the app side has no video paths at all, as in the unified parquet, drop `video` from the
   mapping or set `use_video_path: false`; the unmatched list says so.)
2. **Key** — the normalised `match.keys`. Normalisation makes `Dia_1`, `dia 01`, `1` and `1.0` equal
   and `Grupo_CBD` equal `cbd`, `Tentativa_2` equal `2`; `aliases` bridge real spelling
   differences.
3. **Unique basename** — only with `allow_unique_basename: true`, and only when the name occurs
   exactly once on each side.

**Trial numbers on the app side.** The app does not always know which trial a video was. In this
order, and with every count written into the report notes: an explicit value (a `trial` column in
the unified file, a `Tentativa_N`/`Trial_N` folder in the results), a number in the experiment id
or video path (`..._Trial_2`, `Tentativa 3`), and finally the **order** of the videos within their
group/day/subject (by experiment id, numbered from 1; only where that group/day/subject repeats).
The order is a guess at the lab's numbering — check the note and the `pairs_*` tab before trusting
it, and prefer naming the trial in the video or folder.

A row with several candidates, or two lab rows claiming one app row, is **ambiguous and matched to
nothing** (two trials of one animal on one day are ambiguous unless `trial` is a key). Rows without a counterpart are listed on both sides (report and workbook): read that list
first, it is the usual reason numbers look wrong.

## 3. Running it

Everything is read-only. In a git worktree run `source scripts/wt-env.sh` first
(`. .\scripts\wt-env.ps1` in PowerShell); in the main checkout `poetry run python …` works too.

### 3.1 `validate` — the lab's sheets against the app's unified report

```powershell
python scripts/barnes_validation.py validate `
  --mapping C:\lab\barnes_mapping.yaml `
  --unified C:\Projetos\Barnes\unified_reports\total `
  --out C:\lab\validation_run1
```

`--unified` is a `unified*_summary_*.parquet`, or a folder: the **newest** such file below it, by
the run timestamp in its name (then by modification time), is used. The file chosen is the first line
of the report notes, with a warning when it is a partial report (only the selected videos).
The `.parquet` carries the raw column names the tool expects (`group`, `day`, `subject`,
`experiment_id`, `barnes_status`, `barnes_encounter_latency_s`, `barnes_strategy_auto`,
`window_start_s`, …). The `.xlsx`/`.csv` exports use display titles; to read them instead, name those
titles under `app.columns` in the mapping (`app: {columns: {status: "Barnes Status", …}}`). A column
that cannot be found is **listed in the report notes** and left blank — the report never silently
skips a metric. If the censoring flags (`barnes_*_censored`) are missing, they are **derived** as
`latency >= 240 s` (the lab sheet's `censor_at_s`) so a ceiling value never counts as an observation;
the notes say how many were derived.

### 3.2 `recompute` — re-run the analysis only

```powershell
python scripts/barnes_validation.py recompute `
  --mapping C:\lab\barnes_mapping.yaml `
  --results-root C:\Projetos\Barnes `
  --project C:\Projetos\Barnes `
  --set visit_min_cover=0.4 --set entry_absent_s=4 `
  --out C:\lab\recompute_run1
```

It re-runs **the analysis, never the detection**, through the real public entry
(`AnalysisService.run_full_analysis`), with the trajectory, zones and `3c` object sidecar that
already exist, and with `BarnesParams` overrides (`--set KEY=VALUE`, JSON values; a name that is not a `BarnesParams`
field, or a value `BarnesParams` rejects, stops the run). Mirroring the
individual report, it works in the arena's local pixel space and uses the report's pixel/cm rule
(falling back to the table diameter, `--table-diameter-cm`, when the project has no calibration).

* The analysis window is **rebuilt** with `barnes_maze_preset_v2` from the effective entry
  thresholds (`--window preset_v2`, the default) — the entry thresholds live in the window, so this
  is what makes `--set entry_absent_s=…` mean something. `--window project` keeps the window the
  project declares (what the app did), `--window none` analyses the whole recording.
* It runs on **private copies** of the trajectories and sidecars in a temporary folder: your
  results, including any `7_AnalysisWindow_*` file, are never touched.
* Trial type: `--trial-type` (default `training`), `--probe-regex <regex>` to mark videos whose
  result path matches as probe, and the project's own `protocol_inputs.barnes.trial_type` when
  `--project` is given (it wins).
* Identity comes from the `Grupo_*/Dia_*/Sujeito_*` folders, and the trial from a `Tentativa_*` or
  `Trial_*` folder when there is one (otherwise as in "Matching"). A results folder of a single
  video has none: match it by `video` (needs `--project`) or set `allow_unique_basename: true`.
* **Time base.** Each recording is dated from its own clocks — the frame ledger (live), the `3c`
  heartbeat, the trajectory timestamps — never from `settings.video_processing.fps` (the rat videos
  run at ~9.9 fps with a variable frame rate). The report notes give, per video, which clock was used
  and its frame rate and any warning; a recording none of them can date is **refused**.
* Multi-aquarium trajectories are skipped (Barnes is one arena per video).

Without `--mapping` it only writes the recomputed table (`app_results` sheet).

Without `--project` the project's Barnes block is unknown, so the `BarnesParams` defaults apply
(18 holes — the metrics use the count the ROI names describe and warn if it differs — and a 184 cm
table); pass `--project` (or at least `--table-diameter-cm`) for real data.

**Check the tool against the app first.** Run `recompute --window project` with no `--set` on the
same project and compare it with `validate` on that project's unified report: the two should agree.
(The unified summary is computed in the calibration's warped space when the project uses a
perspective homography, so small differences are expected then; without one they should be
identical.) A larger gap means a pixel space, window or trial-type input differs — find out why
before trusting any calibration.

### 3.3 `calibrate` — search the thresholds, hold some videos out

```powershell
python scripts/barnes_validation.py calibrate `
  --mapping C:\lab\barnes_mapping.yaml `
  --results-root C:\Projetos\Barnes --project C:\Projetos\Barnes `
  --seed 1 --calibration-fraction 0.6 `
  --out C:\lab\calibration_run1
```

1. The videos the lab sheets cover are split **by animal** (group + subject), **seeded** and
   **stratified by group**, into a calibration subset (`--calibration-fraction`, default 0.6, of the
   animals) and a held-out subset. A rat has several trials and days: splitting by video would put the
   same rat on both sides and let the thresholds be tuned to it and then "confirmed" on it. Every video
   of an animal goes where the animal goes; a group of two animals keeps one on each side; groups of a
   single animal are pooled. With too few animals the held-out subset can be empty — the report then
   says **nothing was evaluated** (and the command prints a warning) instead of "keep the defaults".
2. The parameters are optimised in three **groups**, in this order, each over the Cartesian product
   of its own grid with the earlier groups fixed at their chosen values:

   | Group | Parameters (current default → default grid) | Judged on |
   |---|---|---|
   | `visits` | `visit_min_cover` (0.3 → 0.2, 0.3, 0.4, 0.5); `visit_enter_frames` (2 → 1, 2, 3); `visit_exit_frames` (3 → 2, 3, 5) — 36 candidates | encounter-latency MAD **and the number of pairs the two sides disagree on being censored**, primary/total-error MAD, probe score / attempts / first-error MAD |
   | `entry` | `entry_min_cover` (0.5 → 0.4, 0.5, 0.65); `entry_max_visible_fraction` (0.35 → 0.25, 0.35, 0.5); `entry_hold_s` (0.5 → 0.3, 0.5, 1.0); `entry_absent_s` (3.0 → 2, 3, 5) — 81 candidates | entry-latency MAD and the number of pairs the two sides disagree on being censored |
   | `strategy` | `center_radius_ratio` (0.5 → 0.4, 0.5, 0.6); `strategy_direct_max_errors` (3 → 2, 3, 4); `strategy_serial_min_adjacent_fraction` (⅔ → 0.5, ⅔, 0.8); `strategy_serial_max_center_crossings` (1 → 0, 1, 2) — 81 candidates | share of strategies that differ from the lab's |

   The "current default" is the project's **effective** `BarnesParams` (its own block over the
   defaults), so a project without overrides starts from the defaults above. A group whose lab data is
   missing (no strategy sheet, no error columns, …) is **skipped**, and said so. `strategy_adjacent_max_step`, `entry_min_reference_frames`, `max_trial_s` and the layout
   parameters are not searched by default.
3. The score of a candidate is the **relative loss**: the mean over the group's metrics of
   `(m + ε) / (m_start + ε)`, where `m_start` is the metric at the group's starting values and ε a
   small constant (0.5 s, 0.05 errors, 0.02 disagreement) so a perfect start does not divide by zero.
   `1.0` = no better than where it started; `< 1` = better. It is scale-free because seconds, error
   counts and a disagreement rate cannot be added. A candidate that leaves any of the starting
   metrics **undefined** (for instance every latency became censored, so no pair is left to compare)
   is **rejected**, not scored on what remains: a threshold must not win by hiding the hard trials
   (the censoring-mismatch term closes the same loophole from the other side).
4. The best candidate wins; **ties go to the one closest to the current values** — the tool does not
   move a threshold without evidence.
5. Finally the defaults and the chosen values are both evaluated on the **held-out** videos. The
   report says, per group, whether the calibrated values improved there (`relative loss < 1`),
   "keep the defaults", or "not evaluated" (no held-out video could judge the group).
   **Only the held-out result counts**; the calibration-subset numbers are optimistic by
   construction.

Options: `--grid grid.yaml` (a map `parameter: [values…]`, replacing or adding axes — only the
parameters above are accepted), `--max-candidates N` (default 500 per group; the run refuses a larger
grid instead of starting something that takes a day), `--seed`. Every candidate re-runs the analysis
of every calibration video, so time ≈ candidates × calibration videos × seconds per video: time a
`recompute` on a handful of videos first and size the grid from that.

The end of the report contains the suggested block, e.g.

```yaml
protocol_params:
  barnes:
    visit_min_cover: 0.4
```

Only parameters that **changed** are listed. It is never written anywhere: put it in the project's
behavioural configuration yourself if the held-out evaluation supports it (and rerun `validate` on
a freshly generated report to confirm).

## 4. Reading the results

### 4.1 Conventions

* Every difference is **app − lab**. A positive bias means the app's latency is longer.
* Counts of what was compared are always shown: pairs, lab blanks, app blanks, and the app's
  `status` of the matched rows (`ok`, or e.g. `unavailable:layout_unresolved` — a row the app could
  not compute is *visible*, not dropped).
* **Strategy is compared with the app's automatic result** (`barnes_strategy_auto`), never with a
  manually corrected `barnes_strategy`: a correction made while looking at the lab's answer would
  leak it into the comparison.

### 4.2 Latencies (encounter, entry) and censoring

Three blocks per latency, in this order of importance:

1. **Both observed — the figure to quote.** Pairs where *both* the lab and the app observed the
   event. A latency of 240 s is "did not happen within the ceiling", not a measurement, and is
   excluded here. Shown: n, **bias** (mean difference), **95 % limits of agreement**
   (bias ± 1.96 SD of the differences — Bland & Altman 1986), mean absolute difference (MAD),
   **ICC(2,1)** with its 95 % CI, and Spearman ρ.
   * *ICC(2,1)*: two-way random effects, **absolute agreement**, single measurement (Shrout & Fleiss
     1979, case 2; the CI is McGraw & Wong's F approximation). With rows = trials and the two
     columns = lab and app: `ICC = (MSR − MSE) / (MSR + MSE + 2 (MSC − MSE) / n)`. Because it asks for
     *absolute* agreement, a constant offset between lab and app lowers it (a consistency ICC would
     not). Common conventions (Koo & Li 2016): < 0.5 poor, 0.5–0.75 moderate, 0.75–0.9 good, > 0.9
     excellent — the lab decides what is enough for the protocol.
   * Read the limits of agreement in seconds against what the lab considers an acceptable difference
     between two human scorers.
2. **Censoring agreement.** Over the compared pairs: both observed, both censored, *lab only
   censored* (the lab says the rat never entered, the app measured an entry), *app only censored*,
   the agreement rate and Cohen's kappa. A high lab-only count points at the entry thresholds being
   too permissive (or the lab placing rats by hand); a high app-only count, too strict.
3. **Ceiling-imputed (not observations).** The same statistics with every censored pair kept at the
   ceiling: the lab is set to its `censor_at_s` wherever its row is flagged censored (whatever the cell
   holds, blank included), the app keeps its own value (it writes the ceiling into a censored
   latency). They are shown **only** so the effect of the ceiling can be judged — two censored
   trials "agree" at 240 s trivially, which flatters the numbers. Do not quote this block.

### 4.3 Errors, strategy, probe

* **Error counts** (primary, total): exact-agreement rate, within ±1, MAD, bias and Spearman ρ.
* **Strategy**: observed agreement, **Cohen's kappa** with a large-sample 95 % CI and the 3 × 3
  **confusion matrix** (rows = lab, columns = app). Kappa is undefined when one rater used a single
  label. Pairs where the lab label is blank or unmapped, or the app produced none (a trial with no
  hole visit), are counted separately. Landis & Koch's bands (0.41–0.60 moderate, 0.61–0.80
  substantial, > 0.80 almost perfect) are the usual convention.
* **Probe**: exact-agreement rate of the first-hole score (and of attempts, with MAD and Spearman);
  for the first-error latency, how many trials have both, neither, or only one side present, then
  the usual Bland–Altman/ICC on the trials with both.
* **START offset** (app START − manual START, seconds): mean, median, SD, extremes, 5th/95th
  percentiles and the share of trials within ±0.5, ±1 and ±2 s. A systematic offset of a second or
  more inflates every latency by the same amount and is the first thing to rule out; a large spread
  means the window START (box and experimenter gone, rat visible, held `k_frames`) disagrees with the
  lab's idea of "released".

### 4.4 Things to look at by eye (open questions of the metrics stage)

These are not statistics the tool can settle; the `pairs_*` tabs tell you which trials to open:

* **Probe score formula** (`min(d + 1, 10)`): any systematic gap in the score near the opposite
  hole is the formula, not the detector.
* **Rim chords**: a rat running along the rim from hole −2 to hole 0 passes over hole −1, which counts
  as a visit; compare the errors on those trials with the lab's.
* **Centre-crossing hysteresis**: there is none; a rat hugging the edge of the centre disk can rack
  up crossings and push a serial search to "random". If strategy disagreements cluster there, that is
  the cause.
* **Tail inflating the bbox** (#651) and **trials the lab scored by hand** show up as lab-only
  censored entries.

## 5. A suggested order of work

1. `validate` with the current defaults → the baseline. Read the unmatched list first.
2. `recompute --window project` (no `--set`) → should reproduce step 1 (the parity check, §3.2).
3. `calibrate` on all the matched videos → read the **held-out** section only.
4. If a group improved on the held-out videos, apply the block to a copy of the project, regenerate
   the unified report and run `validate` again; if nothing improved, keep the defaults — that is a
   result too.
5. Send the three sheets, the report and the suggested block back to the maintainers so the defaults
   in `BarnesParams` (CONTRACTS §3.2) can be updated with the evidence next to them.

## 6. Limitations of the tool

* It compares one trial per video; multi-aquarium runs are out of scope, like the Barnes metrics.
* The calibration optimises each group on its own lab columns and never tunes against the strategy
  sheet while searching visits; interactions between groups beyond the fixed order are not explored.
* Seeded splits are reproducible (same seed, same files); a different seed will pick different
  animals — a result that depends heavily on the seed means the sample is too small.
* No real lab data is in the repository: every number in the tests is synthetic.
