# Recent Critical Fixes — November 2026

## 0. The nightly memory job never ran the suite to the end

**Symptom.** From 2026-09-17 to 2026-11-13 the `Memory Leak Detection` job of
`.github/workflows/stress-tests.yml` failed every night and opened a new
`Nightly memory profiling run failed` issue each time: 56 identical issues
(#576 and its duplicates). The date matters. PR #573 had fixed the artifact
upload and added the gate that fails the job when `pytest --memray` fails, so
from the next night on the job reported its real outcome. The profiled run had
never passed. #573 only made that visible.

**No leak was measured.** Every run died at about 90% of the suite in one of two
ways:

- **Timeout** (most nights).
  `tests/ui/dialogs/test_block_detail_dialog_extended.py::test_block_detail_dialog_init_int_day`
  hung until `pytest-timeout` (300 s, `thread` method) killed the process. The
  main-thread stack ended in `tkinter.Misc._root()`:
  `while w.master is not None: w = w.master`, with every `.master` produced by
  `unittest.mock`.
- **Abort** (#576, #620, #660). `Fatal Python error: Aborted` in
  `tests/ui/components/test_single_video_workflow_ui.py`. The thread that hit
  the abort was a `Camera._reader_thread`, in the middle of a garbage collection.

**Root cause 1: the job had no display.** `ci.yml` and the `mutation-catalogue`
job run the suite under `xvfb-run`. The memory job did not. Without a display,
`tests/conftest.py` sets `HEADLESS_TESTS = True` and the Tk root becomes
`_create_mock_tk_root()`, a `MagicMock`. CI never runs in that mode. The mock
had no `master = None`, so `root.master` returned a fresh mock, whose `.master`
was another mock, and so on without end. Any widget built over it looped forever
in `_root()`. This reproduces locally:
`ZEBTRACK_HEADLESS_TESTS=1 pytest <that test> --timeout=20` hangs, and the same
test passes in 9 s on a real Tk.

**Root cause 2: three tests leaked camera reader threads.** `Camera.__init__`
starts `_reader_thread`. Three tests in `tests/test_io_sources.py` built a camera
over a mocked `cv2.VideoCapture` that returns `(True, MagicMock())` forever, and
never called `release()`. Those threads spun through the rest of the session,
allocating mocks. The thread dumps of every failed run show exactly these three
threads. Under memray their allocations triggered garbage collection on that
thread, and when the collection finalized Tk objects off the main thread, Tcl
aborted the process. The 2026-09 investigation could not find these threads
because it measured the wrong test directories.

**Fix.**

- The memory job installs `xvfb ffmpeg libavcodec-extra` and builds the template
  archive and the translations, as `mutation-catalogue` does. It then runs
  `pytest --memray` under `xvfb-run`.
- `_create_mock_tk_root()` sets `root.master = None`, so headless mode can no
  longer hang. Guarded by `tests/test_conftest_headless_root.py`.
- The three tests release the camera in a `finally` block. The first one now
  asserts that the reader thread is dead after `release()`.
- `stress-tests.yml` opens each nightly issue at most once. The shared helper
  `.github/scripts/file_nightly_issue.js` comments on the open issue with the
  same title when there is one, so a persistent failure keeps a single history.

**Third cause, found once the suite reached the end.** The first run on the fix
branch got through the whole suite under memray, with one failure:
`test_failed_replace_cleans_the_temporary_file` patched `os.replace` to raise
unconditionally. `artifact_module.os` is the `os` module itself, so the patch
applied to the whole process. pytest-memray renames its per-test result file
with `os.replace` inside the same call phase, and got the test's
`PermissionError`. The stub now raises only for the artifact's own destination
and passes every other call through to the real function.

**The other two stress jobs never ran either (#685).** `threading-stress` and
`flakiness-detection` passed `--count=N`, but `pytest-repeat` was not a project
dependency. pytest died on `unrecognized arguments: --count` before collecting a
test, and `continue-on-error: true` reported both jobs as green. #625 was the one
night the threading job went red, and only because PyPI dropped the connection
during `poetry install`. Running them for real exposed two more problems that were
not in the product:

- Under `--count=3`, the coverage tracer aborted the process (SIGABRT) inside a
  threaded camera test. Both jobs now pass `--no-cov`.
- pytest-repeat gives each repetition of a `@given` test a fresh class instance,
  which Hypothesis's `differing_executors` health check rejects. The flakiness job
  loads `tests/pytest_repeat_hypothesis.py`, which suppresses only that check.

Both jobs now have the same display setup as the memory job, and a gate step
that fails the job when pytest fails.

**The first fully passing run was cancelled by the clock.** Run 43428147257 reached
99% of the suite under memray, with 7987 passed and 0 failed, and was then cancelled
by the job's `timeout-minutes: 45`: setup takes ~4 min and the suite ~42 min when
memray tracks every allocation. A job cancelled that way also bypassed the alarm,
because the gate and the `if: failure()` issue step are both skipped on
cancellation. The memory job now has 75 minutes. Every issue step also fires on
`cancelled()` in scheduled runs, so a nightly timeout files an issue, while
cancelling a manual run by hand does not.

**Cancelled by the clock again (#741).** Run 374 (45926639906, 2026-11-27) was
cancelled at 88 % of 11080 selected tests (9792 passed, 0 failed): the pytest step ran
02:11:46 to 03:24:29 (72.7 min), so the full suite under memray takes ~83 min, not 42.
The job limit is now 140 min (3 setup + 83 x 1.1 growth ~= 94 min, ~1.5x headroom) and
the run step has its own 125 min limit, so hitting it fails the step instead of
cancelling the job and the uploads and the issue step still run. The issue now says
"did not finish - timeout or cancelled" when `memory-leak-results.xml` was never
written, instead of implying a leak. Past ~2 h, shard by test directory.

## 1. The flakiness job aborted every night in an innocent camera test (#735)

**Symptom.** From 2026-11-20 the `Flakiness Detection (3x full suite)` job died at ~62 % of
the suite, every night, with exit code 134:

```text
Tcl_AsyncDelete: async handler deleted by the wrong thread
Fatal Python error: Aborted
Current thread ... (most recent call first):
  Garbage-collecting
  File ".../src/zebtrack/io/camera.py", line 349 in _capture_frame
  File ".../src/zebtrack/io/camera.py", line 167 in _reader_thread
```

Seven nights, same place (`tests/io/test_camera.py`, runs 44221117005 → 45740487197; the
last one is job 139643980896). The camera tests were the **victim**: their reader thread
allocates a mock call per frame, so it is the thread most likely to trigger a cyclic
collection, and whoever runs the collection frees what it finds. A Tcl interpreter freed on
a thread other than the one that created it makes Tcl abort the process, **even after
`destroy()`**. `destroy()` removes the window. The interpreter dies only when the Python
object is freed.

**Root cause.** `ROITemplateManager.__init__` (`ui/components/roi_template_manager.py`) built
a private `tkinter.Tcl()` whenever its parent had no real Tk root, "to avoid default-root
failures in headless tests", and never destroyed it. A probe that wrapped `tkinter.Tk.__init__`
over the 6 736 fast tests that run before `test_camera.py` found exactly one interpreter
created: by that fallback, in
`tests/integration/test_zones_updated_event.py::...::test_roi_template_manager_publishes_zones_updated_dual_mode`.
The interpreter outlived the test. The patched `StringVar` mock recorded it in `call_args`, and
ttkbootstrap's theme `Publisher` keeps the newest root by its Tcl name `"."`. Several hundred
tests later a collection on the camera thread finalised it. Running just those two files
with `--count=3` aborted 2 runs out of 3 on Windows. With the fix, none of 14 runs aborted.

The #685 entry above blamed "the coverage tracer" for a SIGABRT "inside a threaded camera
test". That was this same abort. `--no-cov` only moved it.

**Fix.**

- Without a Tk master, `ROITemplateManager` keeps the selection in `_FallbackStringVar` and
  creates no interpreter. `template_var` is never bound to a widget, and the app always
  passes its real root, so production behaviour is unchanged.
- **Guard** (`tests/tk_interpreter_guard.py`, autouse in `tests/conftest.py`): every
  `tkinter.Tk`/`Tcl()` created during a test is recorded by weak reference. At teardown,
  one the test left alive is collected *on the main thread*, and the test fails, showing the
  line that created it. The `tkinter_session_root` root is exempt. ttkbootstrap's registry
  entry for that root is dropped first, because that hold is ttkbootstrap's, not the test's.
  The crash names whoever happened to collect, so only a per-test check can name the culprit.
- `test_reconnect_abort_still_stops_when_the_driver_release_fails` called
  `_handle_reconnect_abort()` from the test thread while the reader thread was still
  streaming. A `read()` already in flight then set `_frame_available` back to `True`.
  This was the next flaky failure the 3x run would have stopped on (`-x`). The abort
  now runs on the reader thread, as it does in production.
